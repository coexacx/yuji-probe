# Rust / Go 主控：200 节点与 200 并发客户端对照压测

完成时间：2026-09-30T07:26:46+08:00。

**结论：当前 Rust 主控节省内存，但本次高并发看板负载中，Go 主控吞吐与响应延时明显更好。** Rust 成功吞吐比 Go 低约 74.8%，主控平均 RSS 低约 53.9%，P95 延时约为 Go 的 4.23 倍。此结论针对实际测试的主控版本和配额，不能由此前 Agent 的比较结果替代。

## 方法

- 使用开发服务器上的独立实例，CPU 为 4 个 Xeon E7-4830 v3 虚拟核心、约 16 GiB 内存；仅监听回环地址。未向生产站或测试站的实际服务施压。
- Go 使用测试主控迁移前保留的实际二进制，构建工具链 Go 1.27.1；Rust 使用已发布的 **0.4.0-rust.1**，没有为本次成绩另行优化或更换程序。
- 两版共用相同 PHP 8.4 网关、Nginx 配置、初始节点状态、模拟器及 TLS 校验。主控各限 **1 核 CPU、512 MiB 内存**；PHP 为 8 个进程、1 核配额；Nginx 0.5 核；压测进程 1 核。整个测试组限制为 2.75 核、2.5 GiB，并仅允许使用 CPU 1～3。
- 每轮建立 **200 条独立身份的 WSS 节点连接**，每个节点每秒集中上报一次 CPU、内存、Swap、磁盘、网卡计数与速率。每秒约 200 条监控消息。
- **200 个模拟 HTTP 客户端持续并发访问 `/api/public/nodes`**，每个客户端始终至多一个在途请求，返回的是完整 200 节点看板。每轮实际最大在途请求数均为 200；不是启动 200 个 Chrome 浏览器。
- 节点和客户端各使用独立的真实回环来源 IP，保留应用原有限流；没有伪造受信头部或关闭身份校验。所有 HTTP 状态码与错误均计数。
- 顺序为 **Go → Rust → Rust → Go**，每轮监控预热 10 秒，再为每个客户端预建 HTTPS 连接，正式发起负载 45 秒，等待已发出的请求结束。成功吞吐按实际经过时间（含最后在途请求完成）计算；握手与预热不计入成绩。
- CPU、RSS、PSS 每约 0.5 秒读取一次，主控数字包含监督进程与工作进程。RSS 为两进程驻留内存之和，可能重复计算共享页，PSS 用于补充核对。

## 解释与后续方向

这组负载的瓶颈集中在主控 CPU：两版均接近单核配额，PHP 与 Nginx 均有余量，节点上报保持正常。Rust 的内存优势没有转化为当前实现的看板吞吐优势。

静态复核发现 Rust 看板接口在共享状态锁内构建完整的 `serde_json::Value` 中间树，随后才将其序列化为 HTTP 响应；当前 release 构建使用 `opt-level = "s"`。可优先评估直接序列化、缩短共享锁持有时间、共享只读监控快照与针对速度的构建选项。这里是根据代码提出的排查方向，本轮没有在正式统计期间运行采样分析器，不能宣称某个函数已经占用了确定百分比的 CPU。

本次测试只对照现有版本，未修改或回退线上程序。隔离服务、端口和临时资源配额均已清理，开发站 Nginx、Agent、PHP 服务的 PID、运行状态及重启计数保持不变。短时间闭环压力不能代表长期容量，也不能直接换算为公网访客数；真实页面按刷新间隔轮询的请求频率与这里的连续饱和请求不同。
